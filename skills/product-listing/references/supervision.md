# 派发、监督与恢复

## 职责与运行约束

发布、重试、失败回滚和多步批量写入默认使用总控加执行子智能体。总控负责范围、监督、恢复决策和验收；执行子智能体负责平台操作、飞书写入、保存回执及资源释放。可增加只读核实子智能体，但不得与执行者共用可变页面或同时写业务数据。

- 使用当前可用的多智能体工具。当前环境以 `collaboration.spawn_agent` 派发，`list_agents` / `wait_agent` 观察，`followup_task` 唤醒已结束的执行者。`send_message` 只投递消息，不会唤醒空闲执行者。不要为了内部子任务新建用户聊天。
- 同一批次只允许一个有写权限的执行者。总控不同时点击发布页或写飞书。接替前先确认旧执行者与其未结束工具调用已停止；工具超时或子智能体结束，不能单独证明远端提交未发生。
- 复用原浏览器任务空间，遵守浏览器工具当前文档与控制权规则。不能为恢复或并行绕过任务空间限制；缺少子智能体工具时总控自行执行同一监督流程。
- 用户停止、接管或撤回授权优先于自动恢复。子智能体只能处理总控分配的原范围，不能自行扩大链接清单、更换店铺、价格、库存或发布方式。
- 本技能及状态脚本不是常驻服务。总控仍在运行时主动监督并续跑；整个应用或总控进程退出后不能自行唤醒。再次调用时读取落盘清单恢复，不声称已设置后台守护或定时任务。

## 启动与派发

1. 读取平台和飞书流程，固定本次记录 ID 清单，保存任务约定：目标 Base／店铺、授权操作、发布方式、候选规则、是否要求最终入仓／在售，以及明确停止条件。已有本批次清单时先读它，禁止重新初始化覆盖进度。
2. 在当前任务的运行目录保存 `request.json`、`state.json` 和必要证据；不要放进技能安装目录或提交到代码仓库。内容只包含记录标识、步骤与必要回执，不保存密码、令牌或整页无关个人数据。
3. 用[状态脚本](#状态脚本)初始化状态。任务约定和最小派发内容至少包括：技能入口路径、批次状态文件绝对路径、精确记录 ID、当前断点、唯一执行权、不可重提条件及下一步。先取得执行者 ID，再登记 `assign`；执行者只有收到带当前 generation 的执行授权后才能修改外部数据。
4. 子智能体启动先重读状态和当前相关页面／记录，核对 revision 与 generation，报告当前步骤。不要依赖旧截图、失效定位或上一回合的口头总结。

提交前先落盘 `begin_submit`，再点击；收到回执立即保存 `receipt`，随后回写飞书并读回。即使只落盘了提交意图、尚不能证明点击发生，也按结果不明处理，先查证再决定重提。已有平台商品 ID 后，回写失败只重做回写，不再发布商品。

## 监督循环

总控派发后必须在当前任务内运行以下循环，不能派发即交付：

1. 有界等待执行者消息，并读 `inspect` 的进度、revision、步骤及下一步。关注实际进展，不把频繁心跳当成果；平台预计处理窗口尚未到期时按核实队列等待，不误判卡死。等待期间按当前运行环境要求提供必要进展更新。
2. 子智能体仍在执行时不给第二个执行者写权限。发现停在同一动作、长时间无新证据或工具超时，询问当前工具状态并排查；必要时中止并确认旧执行已停止后接替。
3. 子智能体 `done`、`interrupted`、异常或提前给出最终回复时，逐条核对业务状态。只要仍有可执行动作，使用 `followup_task` 发送「记录 ID + 已确认步骤 + 新的具体动作 + 避免重提条件」，主动恢复；不能转述报错后让用户说继续。
4. 普通定位、最小化、图片绑定、网络或回写问题按[恢复排查](recovery.md)修复。同一错误再现时更换有依据的排查动作，不无限重复同一点击或空泛的「继续」。恢复次数、耗时、子智能体退出都不是业务阻塞证据。
5. 提交结果不明，按 `reconcile` 动作先查平台回执、现有商品 ID、正确店铺与查询范围。一次查空不能重提；只有可靠证据证明未创建时才能登记 `reconcile_not_submitted` 后重试。其他独立链接继续。
6. 真正阻塞必须有当前证据、明确受影响记录、已尝试动作及下一步。平台限额按实际店铺／类目／商品范围判断，不能把某次数字当通用阈值。只有已确认的共同原因才批量登记 `block`。无关记录继续处理。
7. 完成业务验收和[浏览器收尾](#浏览器收尾)后，检查 `canFinish` 并交付。若状态脚本报告可结束但实际证据不足，继续调查；脚本不能代替总控判断。

真实阻塞包括无法从已授权资料补齐的必填项、平台明确拒绝、需要用户验证的登录问题、确实缺少权限以及浏览器工具要求用户处理的控制权事件。请求必要介入前，完成其他独立工作并交还浏览器控制。用户明确停止时及时停止外部操作，不强行补完业务写入。

## 状态脚本

需要 Node.js，使用技能目录中的 `scripts/run_state.mjs`。脚本只记录和校验状态，不调平台、不启动智能体，也不会替总控运行监督循环。

```text
node <skill-dir>/scripts/run_state.mjs init <run-dir>/state.json <run-dir>/request.json
node <skill-dir>/scripts/run_state.mjs inspect <run-dir>/state.json
node <skill-dir>/scripts/run_state.mjs apply <run-dir>/state.json <run-dir>/event.json
```

请求示例：`{"batchId":"batch-example","recordIds":["record-a","record-b"],"requireFinalVerification":false}`。范围固定且去重，`requireFinalVerification` 按用户要求设置。

每个事件携带最新 `expectedRevision`；执行者事件还要携带 `workerId`、`generation`，逐条事件携带 `recordId`。先 `inspect` 再写事件 JSON 文件，避免在 shell 中插入业务文本。并发 revision 冲突时重读状态，禁止覆盖较新结果。

| 事件 | 何时登记与必要信息 |
|---|---|
| `assign` | 总控分配唯一执行者 `workerId`；接替时需 `previousWorkerStopped:true`，必须先有实际停止证据。 |
| `worker_report` | `kind:running/interrupted/done`；仅是执行者状态，不代表业务成功。 |
| `step` / `fault` | 实际步骤 `step,progressKey` 或错误 `code,message,recoverable`；有意义的新进展才更新 progressKey。 |
| `begin_submit` | 点击提交前保存唯一 `attemptId`；此后无明确结果必须先核实。 |
| `receipt` | 保存平台 `itemId,evidence`；尚在处理时另记 ISO 格式 `nextCheckAt`。 |
| `existing` | 查重发现历史商品时保存 `itemId,evidence,nextCheckAt`（可选），不登记新的提交意图，不计本次新增。 |
| `verify` | 保存匹配的 `itemId`、`outcome:warehouse/on_sale` 和 `evidence`。 |
| `writeback` | 实际写入且读回一致后登记 `evidence,readbackConfirmed:true`；平台状态更新后重新回写。 |
| `reconcile_not_submitted` | 总控有确凿未创建证据后登记 `recordId,evidence,conclusive:true`。一次搜索为空不满足。 |
| `block` | 总控核实 `recordIds,kind:platform/auth/missing_input/control,evidence,nextAction`。已有商品 ID 时必须注明 `stage:verification/writeback`；提交结果不明时用 `stage:submission_resolution`，保留未知结果。只有平台明确提交被拒才加 `submissionRejected:true`。 |
| `unblock` | 总控确认问题已解除后保存 `recordIds,evidence`，恢复原断点。未知提交仍先核实，已有商品只补核实／回写；不得重置状态文件。 |
| `stop` / `resume_user` | 保存用户停止／明确恢复授权的 `evidence`。用户接管后不能由总控自行恢复授权。 |
| `control_acquired` | 得到浏览器控制时立即记录 `spaceId,evidence`，资源收尾义务独立于业务进度。 |
| `control_released` | 真正执行释放并核实后保存 `method:finish/handOff,evidence`，不能用本事件代替浏览器调用。 |

阻塞记录也需要回写；确因认证或控制权问题无法回写时，用当前证据记录 `writebackUnavailableEvidence`，不可虚构写回成功。保存并核对尚在平台处理中的回执和下次查询时间；仅要求提交时可交付「已提交、待核实」，要求最终结果时必须继续核实。脚本拒绝旧 generation 写入；这只是本地防护，不能阻止旧执行者已经发出的远端请求，总控仍须确认旧执行者停稳。

`inspect` 的 `actions` 按记录给出下一步；`origin` 区分本次新建与历史商品，阻塞时 `businessStatus` 保留已确认的业务阶段。总控汇总时同时检查这些字段和原始证据，不把暂停核实的已提交商品统计为未提交。

`worker_report:done` 表示执行者停止业务操作。收尾由已停止的执行者在总控指令下仅执行释放，或由总控在确认无并发操作后接手；不要为做清理把它重新标为正在处理业务。若 `.lock` 文件残留，先核对其中进程确已停止且无其他写入者，再移除该锁并重读状态；不能看到锁就直接删。状态文件不存在、损坏或版本不支持时，从已保存回执和平台／飞书证据重建，不从头盲目提交。

## 浏览器收尾

收尾归总控验收、由当前唯一执行者操作；执行者已停止且无人再操作时总控可以接手收尾。执行者汇报「完成」不免除总控检查资源释放。

1. 操作前阅读当前 `ego-browser skill`。记录本任务空间 ID 和是否取得控制；不得清理用户其他任务空间。普通可恢复中断仍在原空间续跑，不因子智能体结束就关页、创建新空间或提前结束任务空间。
2. **业务成功完成**：保存回执及结果页后，按当前工具文档调用原任务空间的 `task.finish({keep:[...]})` 一次，只保留用户需要的结果页。完成后不再操作该空间的页面。
3. **真实阻塞退出、需用户介入、用户停止／接管**：按当前工具文档调用 `task.handOff()` 归还控制，保留现场供用户接手；不能把中断包装成成功而调用成功收尾。用户已接管时先读所有权，不强行重新获取控制。
4. 用 `listTaskSpaces()` 等只读方式核实原空间不再由 agent 控制；记录实际所有权（例如 `agentDelegatedToUser`）或成功结束结果。若仍显示 agent 控制，检查是否有未结束的子智能体／工具调用，安全停止后按工具文档修复释放。不要为了验收又获取页面控制。
5. 释放调用失败或超时，先查所有权，防止已经结束后重复 `finish`。仍有控制时继续排查，不能只写清理事件就报告成功。工具完全不可用时保存释放错误和空间标识，明确汇报未能确认释放，不虚报已归还，也不无限空转。
6. 核实释放后登记 `control_released`，`inspect` 应不再出现 `cleanup_required`。最终回复区分本次提交、历史跳过、实际入仓／在售、平台处理中及真实阻塞，并说明需用户介入的最小动作。

禁止用退出店铺登录、清除 cookie、杀浏览器进程或关闭全部标签代替释放控制。技能测试也遵守收尾要求；无浏览器的模拟测试应明确未建立真实控制连接。
