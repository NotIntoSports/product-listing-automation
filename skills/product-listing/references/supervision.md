# 派发、监督与验收

本文件供总控使用；执行者按派发任务读取平台、数据及状态接口。总控只在验收证据冲突或需要接手时查业务细节，不要求双方启动时都读全套文档。

## 启动与派发

1. 固定授权约定：目标 Base／店铺、记录 ID 范围或候选筛选、操作与发布方式、是否跟到最终状态。需要查候选时先派发只读准备任务，取得完整候选及查重证据后固定清单，再授权写入。已有断点先恢复，禁止重新初始化覆盖。
2. 在任务运行目录保存约定、状态和必要证据，不写入技能目录或代码仓库，不保存凭据。发布／核实批次用[状态接口](state-api.md)，纯资料维护用逐条写入与读回清单，不伪造平台回执。工具输出保持摘要；需要某条证据时用 `inspect --record`，最终全量对账才用 `--full`。
3. 派发唯一执行者，取得其 ID 后登记 `assign`，再发送带当前 generation 的写入授权。派发内容包含技能入口、角色、约定与状态文件绝对路径、精确范围、当前断点及下一步。支持时为新执行者使用独立上下文（如 `fork_turns:"none"`），传所需文件路径和事实，不复制整个聊天或手册。
4. 同一批次只有一个写入者。总控不与执行者同时操作发布页或写飞书；核实者只能在隔离环境只读。更换执行者前确认旧执行者及未结束工具调用停稳，再换 generation；本地代次校验不能取消已发出的远端请求。没有子智能体工具时，总控按相同闭环自行执行。

当前工具中，`collaboration.spawn_agent` 派发，`list_agents` / `wait_agent` 观察，`followup_task` 唤醒空闲执行者；`send_message` 只传消息、不唤醒。不为内部子任务新建用户聊天。

## 监督循环

派发后在当前任务中持续监督，不能派发即交付：

1. 有界等待消息，以 `inspect` 的 revision、counts、nextAction 和调度动作检查实际进展。执行者仍运行时先观察；预计平台处理窗口未到时按最早查询时间等待，不当成卡死。摘要不是逐条证据，不能仅凭计数验收。
2. 执行者结束、异常或超时后，核对断点及未结束工具。仍有可执行步骤就用 `followup_task` 下发「记录 ID、已确认步骤、具体动作及不可重提条件」，主动续跑，不让用户再说继续。同一错误重现时调查原因、更换有依据的恢复动作，不无限重复点击；具体故障发生后读[恢复排查](recovery.md)。
3. `reconcile` 表示提交结果不明：先查回执、商品 ID、正确店铺与查询范围。一次查空不能重提；只有确凿未创建证据才能恢复提交。已有商品 ID 而回写失败，只补回写。其他独立链接继续。
4. 真正阻塞需当前证据、受影响记录、已尝试动作及下一步；如不可补齐的必填项、平台拒绝、登录验证、权限或工具控制权要求。共同问题只标记明确受影响的记录，不套用历史限额。恢复次数、耗时或子智能体退出不能代替阻塞证据。
5. 用户停止／接管时立即停止自动续跑及外部操作，保存断点、归还现场；只有用户明确恢复才登记 `resume_user`。普通可恢复中断保留原任务空间，不能借新空间绕过工具限制。

本流程和脚本不提供进程外守护；整个应用或总控进程退出后，下次调用再从断点恢复，不宣称后台仍在运行。

## 业务验收与汇报

- 最终对账覆盖固定清单全部记录，结果合计等于范围。按需读取单条证据或一次全量决策，核对记录 ID、商品 ID、观测时间及写后读回；旧查询不得覆盖新结果。历史商品单列，不计本次新增。
- 子智能体 `done` 不代表业务完成。仍有可执行步骤就继续；缺原因的「尚未提交」「填写中」不是交付。只要求提交时，全部即时回写及到期核实完成后，可交付有回执和下次查询时间的待核实项；要求最终状态则继续跟进。
- 真正阻塞只暂停受影响项，先完成其他独立工作。汇报区分本次提交、历史跳过、已入仓、已在售、平台拒绝、处理中及结果不明；未完成项给出步骤、是否提交、原始错误、已尝试动作和下一步。原因未知时继续调查，不编造成资料问题。
- 脚本 `canFinish` 是校验辅助，总控仍须查实际证据并完成以下收尾。

## 浏览器收尾

由唯一执行者操作，总控验收；执行者已停稳且无并发调用时总控可接手。操作遵循当前 `ego-browser skill`，只收尾本任务空间，不退出登录、清 cookie、杀进程或关闭全部标签。

1. 取得控制即登记 `control_acquired`。业务操作停止后登记 `worker_report:done`；后续仅释放控制时不重新标成业务运行中。
2. **业务成功**：保存结果后对原空间调用 `task.finish({keep:[...]})` 一次，保留用户需要的结果页；之后不再操作该空间页面。
3. **真实阻塞退出、用户停止／接管或需用户介入**：按工具文档 `task.handOff()` 交还现场，不用成功收尾掩盖中断。已接管则先读所有权，不重新获取控制。
4. 用 `listTaskSpaces()` 等只读操作确认已结束或所有权不再是 agent（如 `agentDelegatedToUser`），再登记 `control_released`。业务完成但未释放时，`cleanup_required` 阻止最终结束。
5. 释放失败／超时先查所有权，避免重复 `finish`；仍被控制则核对残留执行与工具调用后修复。工具完全不可用时记录空间、错误和未确认释放事实，不虚报成功，也不无限空转。确认 `canFinish` 与实际结果一致后交付。
